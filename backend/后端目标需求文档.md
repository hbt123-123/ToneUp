## 1. 文档定位与范围

### 1.1 定位

本文档是 ToneUp 后端的唯一开发依据。凡与根目录《开发需求文档》《数据库结构文档》表述冲突之处，一律以本文档为准。根文档中未被本文档推翻的内容（主要是面向前端的交互约定）继续有效。

《开发需求文档》第 9.1 节的接口命名为正式协议。以下旧路径已废弃，任何代码、测试、文档和客户端不得再使用：

* `/api/meta`
* `/api/practice/submit`
* `/api/review/today`

接口契约最终以 FastAPI 生成的 OpenAPI 文档为准，前端类型由该契约生成。

### 1.2 范围

涵盖：工程结构、题型体系与统一 DTO、数据模型、全部接口契约、客观题判分规则、主观题 AI 判分模块、复习与统计口径、安全与非功能需求、部署运维需求基线、开发批次划分。

不在本期范围：部署实施动作（第 11 章仅描述未来部署时的验收基线）、前端与安卓端实现、题库内容制作。

### 1.3 现状基线

* 题库文件已就绪：`data/math/math1.db`（数学一）、`data/math/math2.db`（数学二）、`data/english/english1.db`（英语一）、`data/english/english2.db`（英语二）。

## 2. 技术选型与工程结构

### 2.1 选型

| 层级 | 选型 | 说明 |
| :--- | :--- | :--- |
| 语言/框架 | Python 3.10 + FastAPI | 异步支持好，自动生成 OpenAPI |
| 包管理 | uv | 锁定依赖，`pyproject.toml` 为唯一入口 |
| 数据校验 | Pydantic v2 + pydantic-settings | 请求/响应模型与环境配置 |
| 数据库 | SQLite3（题库只读 + user_data.db 读写） | 无独立数据库服务 |
| 日志 | structlog（JSON 输出）+ request_id 中间件 | 每请求生成或透传 `X-Request-ID`，注入日志上下文与响应体 `request_id` 字段 |
| 测试 | pytest | 覆盖服务层与仓储层，题库用副本夹具 |
| AI | 智谱 GLM | 模型名仅作配置项，见第 8 章 |

### 2.2 目录结构（分层架构）

```text
backend/
├── pyproject.toml
├── app/
│   ├── main.py            # FastAPI 实例、中间件、路由注册、启动校验
│   ├── api/               # 路由层：参数校验、统一响应封装，不含业务逻辑
│   ├── services/          # 业务层：判分、复习调度、统计聚合、AI 任务编排
│   ├── repositories/      # 数据访问：题库只读仓储、用户库仓储、标签库仓储
│   ├── core/              # 配置、安全(JWT/Argon2id)、日志、连接管理、限流、异常
│   └── schemas/           # Pydantic v2 模型：请求、响应、题目 DTO
├── data/                  # 题库与索引（已存在，只读）
├── scripts/               # init_user_db.py / init_knowledge_tags.py / validate_banks.py
└── tests/
```

分层约束：api 层不直接触碰 sqlite3；repositories 层不做业务判断；services 层可组合多个仓储。所有配置经环境变量注入（`DATA_ROOT`、`JWT_SECRET`、`JWT_EXPIRE_HOURS`、`ZHIPU_API_KEY`、`GLM_VISION_MODEL`、`GLM_TEXT_MODEL` 等），代码中禁止出现密钥与模型名硬编码。

## 4. 题型体系与统一 DTO

### 4.1 题型映射（配置驱动）

`question_type_id` 到 `type_code` 的映射按学科放在配置中（随 manifest 校验加载），客户端只消费字符串 `type_code`，永不解释数字 ID。映射关系与真实数据分布如下（题量为每库约数，已对实际数据库核实）：

| 学科/题库 | question_type_id | type_code | 中文名 | 每库题量(约) | 判分方式 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| math：math1.db 数学一、math2.db 数学二 | 1 | SINGLE | 单选题 | 209 | 服务端自动 |
| math 同上 | 2 | FILL_BLANK | 填空题 | 153 | AI 为主（确定性优先优化） |
| math 同上 | 3 | SOLUTION | 解答题 | 223 | AI 判分 |
| english：english1.db 英语一、english2.db 英语二 | 1 | CLOZE | 完形填空 | 300 | 服务端自动 |
| english 同上 | 2 | READING | 阅读理解(单选) | 300 | 服务端自动 |
| english 同上 | 3 | ORDERING | 新题型排序 | 75 | 服务端自动 |
| english 同上 | 4 | TRANSLATION | 翻译 | 75 | AI 判分 |
| english 同上 | 5 | ESSAY | 作文 | 30 | AI 判分 |

补充事实与约束：

* MULTI、JUDGE 两个 type_code 保留在枚举与映射配置中，供未来题库使用，当前数据中不存在对应题目。
* 年份覆盖：数学两库各 2000 至 2025 年共 26 套；英语两库各 2011 至 2025 年共 15 套。
* 图片为 images 表 BLOB：数学两库约 44/34 张，英语两库约 15/15 张。英语图片带 collection_id/question_id 外键，数学图片可能没有外键，只能由题干内引用关联。
* 数学 FILL_BLANK/SOLUTION 的 answer_text 为 LaTeX 文本；英语 TRANSLATION 的 answer_text 为 markdown 格式参考答案。
* math2 的 content 存在 `### 1.` 之类的 markdown 残留前缀，Repository 层必须清洗（见 4.3）。

### 4.2 双格式 options 归一化规则

两个学科库内 options 的 JSON 形状不同，Repository 层必须归一化为同一种输出：

| 来源 | 库内形状 | 归一化输出 |
| :--- | :--- | :--- |
| 数学 | JSON 对象 `{"A": "$...$", "B": "$...$"}` | `[{"label":"A","text":"$...$"}, ...]` 按 label 升序 |
| 英语 | JSON 数组 `[{"label":"A","text":"..."}]` | 原形状，仅做字段白名单校验后透传 |

统一 DTO 中 options 一律为数组形式。options 或 sub_questions 的 JSON 非法时，该题库在启动校验中标记为不可启用（见 5.5）。

### 4.3 markdown 残留清洗规则

清洗发生在 Repository 读出之后、DTO 组装之前，只影响对外输出，不修改库内原始数据：

1. 去除 content 行首的 markdown 标记（`#`、列表符、加粗星号）及重复题号前缀（如 `### 1.`）。
2. 规则集中在一处实现，提供开关配置以便排查数据问题时关闭。
3. answer_text/solution 属于展示文本，同样过该清洗管线但不做语义改写。

### 4.4 统一题目 DTO

| 字段 | 类型 | 可空 | 说明 |
| :--- | :--- | :--- | :--- |
| bank_id | string | 否 | 业务身份，来自 manifest |
| question_id | int | 否 | 题库内主键 |
| collection_id | int | 否 | 所属试卷 |
| year | int | 否 | 年份 |
| type_code | string | 否 | 见 4.1 映射 |
| number | int | 否 | 题号 |
| content | string | 否 | 清洗后的题干 |
| passage | string \| null | 是 | 仅英语 CLOZE/READING 有值，来自 passages 表 |
| options | array \| null | 是 | 归一化后的选项数组 |
| sub_questions | array \| null | 是 | 解答题小问等复合结构，JSON 透传 |
| display_order | int | 否 | 显示顺序 |

列表接口不返回 answer_text 与 solution；题目详情接口和提交结果接口允许返回（根文档 5.2 已授权）。passage 在列表中默认返回：单卷题量不超过 30 题，体积可控；若 M1 实测超预算，可改为列表返回 passage_id、详情补全，但两个客户端行为必须一致，且需评审记录。

## 5. 数据模型设计

### 5.1 manifest.json 规范与校验

manifest.json 是题库业务身份的唯一来源，数据库文件名与目录层级不参与业务逻辑。结构为 `subjects[]`（含 id/name/icon/types[]，沿用根文档 3.2 示例）加扁平的题库条目数组，每条必须包含：

```json
{ "id": "math1", "subject_id": "math", "type_id": "zhenti", "name": "考研数学一真题", "path": "math/math1.db", "schema_version": 1, "enabled": true }
```

启动与重载时的校验规则：

1. 题库 id 全局唯一；subject_id/type_id 能归属到 subjects 树。
2. path 为相对数据根目录的相对路径，resolve 后必须仍位于 DATA_ROOT 内，拒绝任何穿越写法。
3. 文件存在且为合法 SQLite；必需表与字段齐全；options/sub_questions JSON 合法；collection 关联完整；display_order 可排序；images.mime 为合法 MIME。
4. 任一条目校验失败只禁用该条目并告警，不影响其他题库启用。
5. 用户数据表只保存稳定的 bank_id，绝不保存真实路径。

### 5.2 user_data.db 表定义（DDL 级字段描述）

**users**

| 字段 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |

| username | TEXT | NOT NULL UNIQUE | 注册时拒绝重名 |
| password_hash | TEXT | NOT NULL | Argon2id，见 10.1 |
| role | TEXT | NOT NULL DEFAULT 'user' | 取值 user/admin，D4 决策 |

**practice_records**（答题流水）

| 字段 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 即 attempt_id |
| user_id | INTEGER | NOT NULL REFERENCES users(id) | |
| bank_id | TEXT | NOT NULL | 不存文件路径 |

| is_correct | INTEGER | NULL | 0/1；NULL 表示待判分 |

**user_notes**

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |

| note_text | TEXT NOT NULL | 笔记正文 |
| updated_at | TEXT NOT NULL | |

**ai_feedback**（AI 判分与拍照诊断，按《数据库结构文档》5.4 建表）：id(TEXT PK)、user_id、attempt_id、bank_id、question_id、status、image_path、is_correct、error_reason、tag_ids_json、raw_response、error_message、created_at、completed_at，附 `(user_id, created_at)` 索引。大段 AI 原始输出独立存表，不塞进 practice_records。

连接约定：user_data.db 启用 WAL 模式与 busy_timeout，写操作走事务。

### 5.3 knowledge_tags.db

两张表，随代码交付初始化脚本 `scripts/init_knowledge_tags.py`，首次建库即为空表（D5 决策），标签内容由人工或批量脚本后续填充：

```sql
CREATE TABLE tags (
    id        INTEGER PRIMARY KEY,
    subject   TEXT NOT NULL,
    parent_id INTEGER REFERENCES tags(id),
    tag_name  TEXT NOT NULL,
    UNIQUE(subject, parent_id, tag_name)
);
CREATE TABLE question_tags (
    bank_id     TEXT NOT NULL,
    question_id INTEGER NOT NULL,
    tag_id      INTEGER NOT NULL,
    source      TEXT NOT NULL DEFAULT 'manual',
    confidence  REAL,
    created_at  TEXT NOT NULL,
    PRIMARY KEY (bank_id, question_id, tag_id)
);
CREATE INDEX idx_question_tags_tag ON question_tags(tag_id);
```

约束：source 取 manual 或 ai；AI 写入前必须校验 tag_id 存在于 tags 表且属于当前学科。标签为空时 AI 判分流程照常执行，tag_ids 返回空数组即可，不得阻塞判分。

### 5.4 只读题库连接约定

* 以 URI 只读方式打开（`file:...?mode=ro`），并执行 `PRAGMA query_only = ON` 双保险。
* 连接经 `functools.lru_cache(maxsize=5)` 管理，闲置由缓存淘汰释放；上限 5 对应四库加余量，见 10.4 内存预算。
* Repository 层屏蔽数学/英语库的结构差异（passages 有无、images 外键有无），向上输出 4.4 统一 DTO。

## 6. 接口契约全量定义

通用约定：除 register/login 外均需 `Authorization: Bearer <token>`。响应统一外层 `{"success":true,"data":{},"message":"","request_id":"..."}`；列表放 `data.items` 并带 `total`、`has_more`。基础错误码 400 参数错误、401 未认证、403 无权限、404 不存在、500 服务器错误；限流超限返回 429，异步受理返回 202。分页参数 page 默认 1、page_size 默认 20 上限 100。

### 6.1 认证

| 方法/路径 | 入参 | 出参要点 | 错误码 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| POST /api/auth/register | body: username, password | 成功创建用户 | 400 用户名已存在/格式非法 | 限流见 10.3；密码强度最小 8 位 |
| POST /api/auth/login | body: username, password | access_token、token_type、expires_in | 400/401 凭证错误 | 令牌必须带过期时间 |
| GET /api/auth/me | 无 | 当前用户 id、username、role | 401 | |

### 6.2 目录与题库

| 方法/路径 | 入参 | 出参要点 | 错误码 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| GET /api/catalog | 无 | subjects/types 树及各题库摘要(id、name、enabled) | 401 | 数据源为 manifest.json，不查库 |
| GET /api/question-banks/{bank_id} | path: bank_id | 题库详情、可用年份区间、题型分布 | 404 | bank_id 未在 manifest 时 404 |
| GET /api/question-banks/{bank_id}/questions | query: year, type_code, page, page_size | 分页题目列表(data.items/total/has_more)，不含 answer/solution | 404 | type_code 合法性校验 |
| GET /api/question-banks/{bank_id}/questions/{question_id} | path | 完整详情：含 passage、归一化 options、answer_text、solution | 404 | 明确授权的详情出口 |

### 6.3 图片（新增端点，D3）

| 方法/路径 | 入参 | 出参要点 | 错误码 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| GET /api/images/{image_id} | path: image_id；query: bank_id(必填) | 流式返回 BLOB，Content-Type 取库内 mime | 404 | |

要求：各题库 image_id 空间相互独立且会重叠，故 bank_id 必填用于定位题库；服务端校验该图确属于该启用题库后才返回。响应带长缓存头（图片内容不可变，建议 `Cache-Control: public, max-age=31536000, immutable` 与 ETag），支持前端懒加载。Repository 层负责把题干中的图片引用改写为本端点 URL（引用格式以 M1 阶段对实际数据的勘察为准）。

### 6.4 答题

| 方法/路径 | 入参 | 出参要点 | 错误码 | 备注 |
| :--- | :--- | :--- | :--- | :--- |

### 6.8 AI 反馈

| 方法/路径 | 入参 | 出参要点 | 错误码 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| POST /api/ai/feedback | multipart: file, bank_id, question_id, attempt_id(可选) | 小图同步返回结果；否则 202 + feedback_id | 400 类型/大小/尺寸超限, 429 | 限流见 10.3 |
| GET /api/ai/feedback/{feedback_id} | path | status 及判分结果 | 404/403 仅本人 | 轮询入口之二 |

上传约束：类型限 jpeg/png/webp，大小 ≤5MB，最长边 ≤4096px，超限直接 400 不落盘。

### 6.9 管理接口（role=admin，D4）

| 方法/路径 | 入参 | 出参要点 | 错误码 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| POST /api/admin/catalog/reload | 无 | 重载结果摘要 | 403 非 admin | 校验通过后原子替换内存索引，失败保持旧索引 |
| GET /api/admin/health | query: bank_id 可选 | 健康检查任务 id 与即时结论 | 403 | 检查表结构、JSON 合法性、图片 MIME、解析完整性 |
| GET /api/admin/health/{task_id} | path | 异步检查结果 | 404 | 大库检查走异步 |

所有管理写操作记录操作者、时间、来源 IP 与 request_id。

## 7. 客观题自动判分规则

适用题型：SINGLE、CLOZE、READING、ORDERING。判分在 POST /api/attempts 事务内同步完成，立即返回结果。正确答案来自题库 answer_text，Repository 层将其解析为标准结构（选项标签或序列）；解析失败的题目记 error 日志并在健康检查中暴露，不得静默放水。

| type_code | 用户答案格式 | 判分规则 |
| :--- | :--- | :--- |
| SINGLE | `"A"` 单个标签 | 与正确标签全等比对 |
| READING | `"A"` 单个标签 | 同 SINGLE |
| CLOZE | `["B","D",...]` 按空序的标签数组 | 逐空比对；score = 答对空数/总空数 × 题目分值；is_correct 仅当全部正确 |
| ORDERING | `["3","1","2",...]` 顺序数组 | 与标准顺序逐位比对，完全一致才 is_correct |

CLOZE 采用部分给分是因为完形每空独立计分符合考研评分惯例；is_correct 保持全对口径以保证复习调度的简单一致。判分结果写入 practice_records 并更新 user_mastery；答错的客观题进入复习池（见 9.1）。

## 8. 主观题 AI 判分模块

适用题型：FILL_BLANK、SOLUTION、TRANSLATION、ESSAY。原则：AI 判分为主（D2）。

### 8.1 流程（文字版）

```text
提交主观题作答
  → 创建 practice_records(is_correct=NULL 待判分)
  → 创建 ai_feedback(status=queued)
  → 后台任务取出：
      读取题干 content + 参考答案 answer_text/solution
      读取 knowledge_tags.db 中该学科标签列表
      构建约束 Prompt(System + User + JSON Schema 要求)
  → 调用智谱 GLM
      含图片输入 → GLM_VISION_MODEL (glm-4.6v-flash)
      纯文本判分 → GLM_TEXT_MODEL (glm-4.7-flash)
      （两者均为配置项，禁止硬编码）
  → JSON Schema 校验输出 {score?, is_correct, error_reason?, tag_ids?[]}
  → tag_ids 存在性校验：过滤不存在或不属于当前学科的标签
  → 回写 practice_records(is_correct/score)、更新 user_mastery
  → ai_feedback 置 succeeded(含结果) 或 failed(含 error_message)
  → 客户端轮询 GET /api/attempts/{id} 或 GET /api/ai/feedback/{id}
```

### 8.2 Prompt 约束策略

沿用根文档第 6 章的 System/User 结构与“只能从给定标签列表选择、严禁捏造”的硬约束，并按题型扩展评分维度：

| 题型 | 评分维度 | 输出要求 |
| :--- | :--- | :--- |
| FILL_BLANK | 最终结果正确性、关键过程 | score + is_correct + error_reason |
| SOLUTION | 结果正确、步骤完整性、逻辑严谨、书写规范 | 按步骤分解给分的 score |
| TRANSLATION | 忠实度、通顺度、重点词句处理 | score + 中文点评 |
| ESSAY | 切题程度、结构组织、语言质量 | score + 中文点评 |

score 取值范围为 0 至题库 score 字段值；error_reason 为面向用户的中文说明。模型返回内容只作为数据入库，不得直接拼接进 SQL 或 HTML。

### 8.3 输出校验与 tag 校验

JSON Schema 校验失败自动重试一次，再失败置 failed。tag_ids 中不存在于 knowledge_tags.db 的条目一律过滤；过滤后为空则存空数组并记日志，不影响 is_correct 与 score 入库。

### 8.4 状态机

`queued → processing → succeeded | failed`。状态持久化于 ai_feedback.status，进程重启不丢任务：启动时扫描处于 processing 且超过 10 分钟的任务，重置为 queued 重新入队；failed 任务保留 error_message 供排查，用户可重新提交。后台并发度默认 1（内存与配额优先），可配置。

### 8.5 FILL_BLANK 确定性优先优化

填空题判分先走确定性归一化比对：去首尾与内部多余空白、去除 `\left`/`\right` 等纯排版命令、全半角与常见等价写法映射（如分数写法）。高置信一致或不一致时直接出结果，不调用 AI；无法判定再回退 AI。此路径是成本与时延优化，不改变“AI 判分为主”的原则；命中情况记日志以便核对准确率。

### 8.6 降级策略（自评兜底）

AI 服务不可用或连续失败时：attempt 保持待判分状态（is_correct=NULL），接口如实返回排队中状态，系统其余功能不受影响；用户可自评兜底，即客户端以 mode=self_judge 再次提交同一题的自评结论，服务端回填原待判分 attempt 并结束其判分状态，不新增流水、不影响幂等键。AI 恢复后后台继续消化积压队列。

## 9. 复习与统计

### 9.1 间隔重复规则

V1 采用固定间隔：答对按 1、3、7、14、30 天递增，答错当天稍后或次日再复习。confidence_level 与间隔对应：

| confidence_level | 含义 | 答对后下次间隔 |
| :--- | :--- | :--- |
| 0 | 新题或刚答错 | 当天稍后或次日 |
| 1 | 初识 | 1 天 |
| 2 | 渐熟 | 3 天 |
| 3 | 熟悉 | 7 天 |
| 4 | 巩固 | 14 天 |
| 5 | 掌握 | 30 天，毕业后不再自动入池 |

FSRS 兼容预留：user_mastery 字段命名保持算法中立，未来引入 FSRS 时仅新增 stability/difficulty 等列，接口字段与响应结构不变。

### 9.2 reviews/today 口径

到期条件 next_review_at ≤ 当前时间，按 next_review_at 升序返回；limit 默认 20 上限 100；subject_id 经 bank_id 到 subject 映射过滤。返回项携带 type_code 与必要题面信息，客户端可直接开练。

### 9.3 skip 语义

POST /api/reviews/{question_id}/skip 将该题顺延，默认 +1 天，可用 next_review_at 覆盖；跳过不计入作答统计、不改变 confidence_level。

### 9.4 weaknesses 聚合口径

聚合维度为 学科 × type_code × 知识点标签。样本窗口取最近 90 天或最近 200 次作答（先到为准）；入选条件：作答次数 ≥5 且正确率 <60%；按错误率降序输出，limit 默认 10。标签维度的数据来自 question_tags 与 ai_feedback.tag_ids_json；无标签数据时该维度置空返回，不阻塞其他维度。

## 10. 安全与非功能性需求

### 10.1 认证与密码

* 密码哈希用 Argon2id（argon2-cffi），参数取 OWASP 下限并适配小内存机器：memory_cost=19456 KiB、time_cost=2、parallelism=1；禁止明文与自制哈希。
* JWT 用 HS256，密钥 ≥32 字符且仅从环境变量读取；access token 有效期默认 12 小时（可配，上限 24 小时）；payload 含 sub、role、exp、iat。V1 不做刷新令牌，过期重新登录。
* 登录失败不区分“用户不存在”与“密码错误”。

### 10.2 路径与注入安全

* 客户端只允许提交 bank_id；服务端以 manifest 白名单解析真实路径，resolve 后强制位于 DATA_ROOT 内。
* 所有 SQL 使用参数绑定；AI 返回内容不得进入 SQL 或模板渲染。

### 10.3 限流清单

| 端点 | 限制 | 维度 |
| :--- | :--- | :--- |
| POST /api/auth/register | 5 次/小时 | IP |
| POST /api/auth/login | 10 次/分钟 | IP + 用户名 |
| POST /api/ai/feedback | 10 次/小时 | 用户 |
| POST /api/attempts | 120 次/分钟 | 用户 |
| 其余接口默认 | 240 次/分钟 | IP |

实现为进程内滑动窗口计数器即可（单进程部署），超限返回 429 与 Retry-After。

### 10.4 内存预算与性能

* 进程 RSS 峰值 <200MB（D6 环境下的硬约束）：Uvicorn 单进程 workers=1；SQLite 连接 lru_cache(maxsize=5)；图片端点流式发送 BLOB，不整体载入内存后再复制；page_size 上限 100；AI 上传图片先校验后落盘并及时释放；禁止一次性 SELECT 整表载入。
* 验收方式：以脚本模拟 20 并发混合浏览与答题，采样 RSS 峰值达标。

### 10.5 日志与备份

* structlog JSON 输出到 stdout；request_id 贯穿请求链路；禁止记录密码、token、图片内容。
* 备份对象：user_data.db、knowledge_tags.db、manifest.json，每日压缩，保留最近 7 天；备份含用户隐私，文件权限收紧并存放于受控位置；题库文件只读，纳入版本管理即可。恢复流程定期演练（见第 11 章）。

## 12. 开发批次建议

### M1：认证 + 目录 + 题目 + 图片 + 客观题判分 + 统计

范围：工程骨架与配置体系；scripts 三件套（init_user_db、init_knowledge_tags、validate_banks）；manifest.json 创建与启动校验；auth 三端点；catalog 与题库三端点；images 端点；attempts 提交与查询（客观题同步判分）；stats 两端点；notes 两端点。

验收标准：

1. 四个真实题库通过启动校验并可分页拉题；数学与英语 options 均归一化为数组；math2 输出无 `###` 残留。
2. 客观题提交幂等：同一 client_request_id 重复提交只产生一条流水，返回首次结果。
3. 图片端点返回正确 mime 与缓存头，bank_id 不匹配时 404。
4. overview/weaknesses 结果与手工 SQL 核对一致。
5. pytest 通过；空载 RSS <150MB，20 并发压测峰值 <200MB。

### M2：主观题 AI 判分 + 复习错题

范围：AI 判分服务与 Prompt 组装；状态机与 ai_feedback 持久化；FILL_BLANK 确定性优先；reviews 两端点；自评兜底；tag 校验。

验收标准：

1. 四种主观题均可提交并进入状态机，轮询能拿到终态与中文 feedback。
2. 模拟进程重启后 queued/processing 任务不丢失并被继续处理。
3. 伪造 tag_ids 被过滤，入库标签全部存在于 knowledge_tags.db。
4. FILL_BLANK 确定性命中时不产生 AI 调用（日志可证）。
5. 关闭 AI 的演练下系统可用：attempt 保持待判分，自评兜底可回填原记录。
6. 复习到期计算符合 1/3/7/14/30 规则，skip 行为符合 9.3。

### M3：管理接口 + 上线准备

范围：admin 三端点与 role 校验；catalog/reload 原子替换；health 异步任务；限流全量启用；备份脚本与恢复演练预案；第 11 章清单评审。

验收标准：

1. 非 admin 访问管理端点一律 403；审计日志含操作者与 request_id。
2. reload 遇到非法 manifest 时旧索引不受影响，修复后可成功替换。
3. health 能检出缺表、坏 JSON、异常 MIME 等注入的故障样例。
4. 各端点限流生效并返回 429。
5. 第 11 章部署需求清单逐项评审通过，形成上线检查记录。
